# Регламент №3. Счета хранения: бизнес-процесс

**Область действия:** открытие счёта хранения в Trigonum и приём цифровых активов на него.
**Предмет:** что происходит на стороне брокера после отправки заявки — до момента, когда средства учтены на брокерском счёте клиента.
**Связанные регламенты:** [№1](./01-dostup-po-etapam-zayavki.md) — право открыть счёт, [№2](./02-urovni-investora.md) — начисление баллов за приток.

---

## 1. Модель хранения

Счёт хранения — **кастодиальный**. Активы лежат на кошельке Trigonum, приватными ключами распоряжается брокер.

Из этого следует важное разграничение, которое нельзя смешивать в интерфейсе и в договоре:

| Что клиент получает | Что это | Что даёт |
| --- | --- | --- |
| **Адрес депозита** | публичный адрес в выбранной сети, закреплённый за клиентом | принимать средства на свой счёт |
| **API-ключ** (опционально) | ключ доступа к счёту через API | читать баланс, инициировать вывод на подтверждённые реквизиты |
| ~~Приватный ключ~~ | **не выдаётся** | — |

Приватный ключ клиенту не передаётся никогда. Передача ключа означала бы некастодиальную модель, в которой брокер не отвечает за сохранность и не может исполнять обязательства по договорам размещения. Формулировка «выдать клиенту ключ» в требованиях всегда означает адрес депозита или API-ключ — это нужно проговаривать явно, потому что цена ошибки здесь юридическая, а не интерфейсная.

---

## 2. Что происходит после отправки заявки

| # | Шаг | Кто исполняет | Результат |
| --- | --- | --- | --- |
| 1 | Регистрация заявки | сервис счетов | заявка со статусом `review`, номер счёта и номер договора зарезервированы |
| 2 | Формальная валидация | сервис счетов | сеть и актив совместимы, сумма не ниже минимума сети, клиент имеет право открывать счёт (регламент №1, уровень A4) |
| 3 | AML-скрининг | комплаенс | санкционные списки, PEP, риск-скоринг заявленного источника средств, сверка с самосертификацией из онбординга |
| 4 | Решение | комплаенс | `contract` — договор сформирован, либо `rejected` с причиной |
| 5 | Формирование договора | сервис документов | PDF из данных заявки, хеш документа зафиксирован |
| 6 | Подписание | клиент | простая ЭП: код подтверждения, хеш документа, отметка времени, IP |
| 7 | Создание счёта и деривация адреса | кастодиальный сервис | адрес выдан, счёт `active` |
| 8 | Регистрация в мониторинге | сервис приёма | адрес поставлен на отслеживание в сети |

**Шаги 3 и 4 — единственные, где возможна остановка.** Всё, что после подписания, выполняется автоматически и без участия человека.

### Автоматическое одобрение

Заявка проходит шаг 4 без ручной проверки, когда одновременно: клиент уже одобрен в онбординге (`APPROVED`), скрининг не дал совпадений, заявленная сумма не превышает порог автоматического одобрения, источник средств совпадает с указанным в самосертификации. В остальных случаях — ручная проверка комплаенсом.

## 3. Как выдаётся адрес

Адрес **выводится**, а не создаётся заново: кастодиальный сервис держит иерархический детерминированный кошелёк (HD-wallet) и выдаёт из него адреса по пути деривации.

```
m / 44' / coin_type' / account' / 0 / index
                ↑          ↑              ↑
             сеть      клиент      индекс счёта
```

Правила:

1. **Один адрес на пару «клиент + сеть».** Клиент с двумя счетами в разных сетях получает два адреса, с двумя счетами в одной сети — два разных индекса.
2. **Адрес не переиспользуется между клиентами.** Иначе невозможно установить отправителя зачисления.
3. **Адрес постоянен.** Клиент сохраняет его в адресной книге и переиспользует. Ротация адреса означала бы потерянные средства при переводе на старый.
4. **Деривация происходит в момент подписания договора**, не раньше. Адрес без правового основания не должен существовать: его появление в системе — уже обязательство принять средства.
5. **Приватный ключ не покидает HSM.** Наружу отдаётся только публичный адрес.

## 4. Приём средств

| Событие | Действие системы |
| --- | --- |
| Транзакция замечена в мемпуле | статус «ожидает подтверждений», клиент видит её в кабинете |
| Набрано N подтверждений сети | зачисление на брокерский счёт по курсу на момент подтверждения |
| Сумма ниже минимума сети | зачисление с удержанием фактической комиссии обработки; при экономической нецелесообразности — возврат по согласованию |
| Пришёл неподдерживаемый токен | не зачисляется, восстановление по отдельному запросу и за счёт клиента |
| Пришло в другой сети | средства недоступны, восстановление невозможно |
| Отправитель не проходит скрининг | зачисление приостанавливается, запрос документов о происхождении |

**Скрининг отправителя обязателен.** Адрес закреплён за клиентом, но это не значит, что переводит именно он. Каждое зачисление проверяется chain-аналитикой на связь с санкционными адресами, миксерами и известными нелегальными сервисами. Совпадение останавливает зачисление до разбора — деньги не возвращаются автоматически, потому что возврат на скомпрометированный адрес сам по себе нарушение.

**Sweep.** Принятые средства переводятся с адреса депозита на общий кошелёк брокера по расписанию или при достижении порога. Для клиента это невидимо: его баланс определяется учётной записью, а не остатком на адресе.

---

## 5. Учёт и последствия

- Зачисление формирует запись в истории операций и увеличивает свободный остаток брокерского счёта.
- Курс фиксируется на момент набора подтверждений, не на момент отправки.
- Зачисление входит в **чистый приток** для начисления баллов (регламент №2, §3.3). Свободный остаток баллов не даёт — они начисляются после размещения в продукт.
- Договор счёта хранения попадает в «Документы» и в журнал согласий с датой подписания и хешем.

## 6. Сроки и статусы

| Статус | Что означает | Норматив |
| --- | --- | --- |
| `review` | заявка у комплаенса | до 1 рабочего дня, автоодобрение — минуты |
| `contract` | договор сформирован, ждёт подписи клиента | бессрочно, напоминание через 3 дня |
| `active` | счёт открыт, адрес выдан | — |
| `rejected` | отказано, с причиной | повторная заявка через 30 дней |
| `suspended` | приём приостановлен комплаенсом | до предоставления документов |

Счёт с нулевым оборотом 24 месяца закрывается, адрес снимается с мониторинга, клиент уведомляется за 30 дней.

## 7. Что нужно от бэкенда

Минимальный контракт под уже реализованный интерфейс:

```
POST   /custody/applications          → { accountId, contractNumber, status }
GET    /custody/accounts              → [ { ...account, address: null | string } ]
GET    /custody/accounts/{id}/contract → PDF
POST   /custody/accounts/{id}/sign    → { status: 'active', address }
GET    /custody/accounts/{id}/deposits → [ { txHash, amount, confirmations, status } ]
```

Требование к контракту: поле `address` отдаётся **только** для счёта в статусе `active`. Фронт не должен получать адрес раньше подписания даже в служебных полях — иначе правило §3.4 перестаёт быть правилом и держится на дисциплине разработчика.

## 8. Состояние реализации

**Реализовано на фронте:** заявка с параметрами и анкетой комплаенса, статусы `review` → `contract` → `active`, формирование и печать договора из данных заявки, подписание с принятием условий, выдача адреса только после подписи, отображение сети, минимума, подтверждений и предупреждения о сети, договоры в «Документах».

**Требует бэкенда:** AML-скрининг и автоодобрение (§2), настоящая деривация из HD-кошелька (§3), мониторинг сети и зачисление (§4), скрининг отправителя, sweep, API-ключи, статусы `suspended` и закрытие спящего счёта.
