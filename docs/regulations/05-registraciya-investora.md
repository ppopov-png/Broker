# Регламент №5. Регистрация инвестора: бизнес-логика

**Область действия:** путь клиента от первого экрана до открытого счёта.
**Предмет:** что происходит на стороне брокера на каждом шаге, как устроены интеграции с провайдером проверки личности и сервисом доставки почты, какие правила действуют на стыках.
**Связанные регламенты:** [№1](./01-dostup-po-etapam-zayavki.md) — что открыто на каждом состоянии, [№3](./03-scheta-hraneniya-biznes-process.md) — счёт хранения после одобрения, [№6](./06-perechen-dokumentov.md) — какие документы требует приложение №1.1 и чего в этом маршруте не хватает.

---

## 1. Кто участвует

| Система | Роль |
| --- | --- |
| Приложение открытия счёта | регистрация и подтверждение почты |
| Кабинет | шаги 3–6 и статус заявки |
| Сервис онбординга | владелец состояния заявки, единственный, кто его меняет |
| **Didit** | проверка личности: документ, селфи, liveness, санкционные списки |
| **Сервис доставки почты** | письма и обратная связь о доставке |
| Комплаенс | решения по заявке |

**Маршрут описан для физического лица.** Ветка юридического лица в продукте существует только как выбор на первом экране: тип клиента нигде не сохраняется, отдельных шагов и документов для компании нет. Разрыв разобран в [регламенте №6](./06-perechen-dokumentov.md).

**Главное архитектурное правило: состояние заявки двигает только сервис онбординга.** Ни фронт, ни провайдер напрямую состояние не меняют — провайдер присылает событие, сервис решает, что оно означает. Иначе подделанный запрос от клиента переводил бы заявку в одобренную.

## 2. Карта состояний

| Состояние | Чем вызвано | Куда ведёт |
| --- | --- | --- |
| `REGISTERED` | форма регистрации | `EMAIL_VERIFIED` |
| `EMAIL_VERIFIED` | переход по ссылке из письма | `IDENTITY_IN_PROGRESS` |
| `IDENTITY_IN_PROGRESS` | создан сеанс Didit | `IDENTITY_VERIFIED`, `IDENTITY_FAILED` |
| `IDENTITY_VERIFIED` | вебхук Didit, решение Approved | `SELF_CERT_COMPLETED` |
| `IDENTITY_FAILED` | вебхук Didit, решение Declined | `IDENTITY_IN_PROGRESS` (повтор) |
| `SELF_CERT_COMPLETED` | анкета самосертификации | `AGREEMENTS_ACCEPTED` |
| `AGREEMENTS_ACCEPTED` | подписаны обязательные соглашения | `EDD_IN_PROGRESS` или `UNDER_REVIEW` |
| `EDD_IN_PROGRESS` | открыта углублённая анкета | `EDD_SUBMITTED` |
| `EDD_SUBMITTED` | анкета отправлена | `UNDER_REVIEW` |
| `UNDER_REVIEW` | заявка у комплаенса | `APPROVED`, `REJECTED`, `AMENDMENTS_REQUESTED` |
| `AMENDMENTS_REQUESTED` | комплаенс запросил уточнения | `EDD_SUBMITTED` |
| `APPROVED` | решение комплаенса | `SUSPENDED`, `REVERIFICATION_REQUIRED` |
| `REJECTED` | решение комплаенса | терминальное |
| `SUSPENDED` | решение комплаенса | `APPROVED` |
| `REVERIFICATION_REQUIRED` | истёк документ или срок проверки | `IDENTITY_IN_PROGRESS` |

Каждый переход пишется в историю: `fromState`, `toState`, время, причина, инициатор. История — источник для трека статуса в кабинете и для разбора обращений.

## 3. Шаг 1. Регистрация

На форме: тип клиента, имя, email, пароль.

Что происходит:

1. Email нормализуется: нижний регистр, обрезка пробелов. Точки и `+`-суффиксы в Gmail **не** схлопываются — это разные адреса с точки зрения права.
2. Проверка на существующий аккаунт. Ответ **не различает** «адрес занят» и «адрес свободен»: иначе форма превращается в перебор базы клиентов. При занятом адресе отправляется письмо «на ваш адрес пытались зарегистрироваться».
3. Пароль хешируется (Argon2id), в открытом виде не хранится и не логируется.
4. Домен адреса проверяется по списку одноразовых почт — регистрация с них запрещена.
5. Ограничение частоты: не более 3 регистраций с одного IP в час.
6. Создаётся клиент, заявка переходит в `REGISTERED`, ставится задача на отправку письма.

---

## 4. Шаг 2. Подтверждение почты

### 4.1. Токен

- Случайный, не меньше 128 бит, из криптографического источника.
- В базе хранится **хеш** токена, не сам токен. Утечка дампа не даёт подтвердить чужую почту.
- Срок жизни 24 часа, использование одноразовое.
- Повторный переход по использованной ссылке показывает «почта уже подтверждена», а не ошибку: клиент часто открывает письмо дважды.
- Просроченная ссылка ведёт на экран с кнопкой «Выслать заново», а не в тупик.

### 4.2. Повторная отправка

Не чаще одного письма в 60 секунд и не более 5 в сутки на адрес. Каждая новая отправка инвалидирует предыдущий токен — иначе действующих ссылок накапливается столько же, сколько писем.

### 4.3. Обратная связь от сервиса доставки

Сервис доставки присылает вебхуки о судьбе письма, и это не декоративная телеметрия — от неё зависит состояние заявки:

| Событие | Что делает система |
| --- | --- |
| `delivered` | отмечает доставку, ничего не меняет |
| `bounce` (постоянный) | помечает адрес недоставляемым, показывает в кабинете «письмо не доставлено», предлагает изменить адрес |
| `bounce` (временный) | повторяет отправку с нарастающей задержкой, до 3 попыток |
| `complaint` | прекращает всю несрочную рассылку на адрес, транзакционные письма продолжаются |
| `open`, `click` | не используются для решений: открытие письма не равно действию клиента |

Постоянный отказ доставки — единственная причина, по которой клиент может **сменить адрес до подтверждения**. Смена инвалидирует все выпущенные токены.

### 4.4. Чего не делаем

Подтверждение почты **не** считается подтверждением личности. Оно доказывает только контроль над ящиком и открывает шаг 3 — не больше.

---

## 5. Шаг 3. Проверка личности (Didit)

### 5.1. Создание сеанса

Клиент нажимает «Начать проверку». Сервис создаёт сеанс у провайдера, передавая внутренний идентификатор клиента в поле поставщика (`vendor_data`) и адрес обратного вызова. Обратно приходят `sessionId` и ссылка на окно проверки.

**Один активный сеанс на клиента.** Повторный запрос при живом сеансе возвращает `409` с идентификатором существующего — клиент продолжает начатую проверку, а не плодит параллельные. Это уже реализовано в мок-слое и должно сохраниться на бэкенде.

Заявка переходит в `IDENTITY_IN_PROGRESS` в момент создания сеанса, а не по факту прохождения.

### 5.2. Статусы сеанса

`NOT_STARTED` → `PENDING` → `IN_PROGRESS` → `COMPLETED` | `FAILED` | `EXPIRED`

`SUPERSEDED` присваивается старому сеансу, когда создан новый. Это отдельный статус, а не удаление: история попыток нужна комплаенсу.

### 5.3. Вебхук

Ключевой канал. Требования к обработке:

1. **Проверка подписи обязательна.** Провайдер подписывает тело запроса общим секретом; запрос без корректной подписи отбрасывается без обработки и логируется как попытка подделки. Без этого кто угодно переводит заявку в одобренную.
2. **Идемпотентность.** Вебхук приходит повторно при таймауте. Обработка идентифицируется парой «сеанс + статус» и выполняется один раз; повторы отвечают `200`, чтобы провайдер прекратил ретраи.
3. **Быстрый ответ.** Вебхук отвечает `200` сразу, содержательная обработка идёт в очереди. Провайдер не должен ждать нашей базы.
4. **Порядок не гарантирован.** События могут прийти не по порядку; переход применяется, только если он вперёд по машине состояний.
5. **Резервный опрос.** Если через 15 минут после `IN_PROGRESS` вебхука нет — опрашиваем статус сеанса сами. Вебхук первичен, опрос страхует.

### 5.4. Решение

| Решение | Состояние | Что дальше |
| --- | --- | --- |
| `Approved` | `IDENTITY_VERIFIED` | открывается шаг 4 |
| `Declined` | `IDENTITY_FAILED` | повтор проверки, причина показывается клиенту |
| `Review` | остаётся `IDENTITY_IN_PROGRESS` | ручная проверка комплаенсом, клиенту показан статус «на проверке» |

**Решение провайдера не единственный источник.** Комплаенс может отклонить заявку с `Approved` от Didit — например, при совпадении по внутренним спискам. Обратное неверно: одобрить `Declined` без ручной проверки нельзя.

**Не более 3 попыток.** После третьего отказа автоматический повтор закрывается, заявка уходит на ручную проверку. Иначе экран проверки превращается в перебор документов.

### 5.5. Данные из проверки

Из ответа берутся: тип и номер документа, ФИО, дата рождения, гражданство, срок действия документа, результат liveness и проверки по спискам.

- Заполняют профиль **в режиме только для чтения**: паспортные данные клиент не редактирует, они приходят из проверки.
- Срок действия документа задаёт дату будущего `REVERIFICATION_REQUIRED`.
- **Изображения документов и селфи у себя не храним.** Храним идентификатор сеанса, решение и извлечённые поля. Минимизация персональных данных — это и требование, и снижение цены утечки.

### 5.6. Повторная проверка

`REVERIFICATION_REQUIRED` наступает при истечении срока документа или срока действия проверки. Счёт при этом остаётся открытым, но приём новых средств ограничивается (регламент №1, уровень A5). Пройденные шаги 4–6 сохраняются: заново проходится только проверка личности.

## 6. Шаг 4. Самосертификация

Клиент заявляет: статус PEP, наличие санкционных ограничений, юрисдикцию, категорию инвестора (`RETAIL` / `PROFESSIONAL` / `INSTITUTIONAL`), при заявке на профессиональный статус — данные об аккредитации.

Ответы решают два вопроса:

1. **Категория инвестора** фиксируется и определяет доступный каталог продуктов после открытия счёта (регламент №1, §4).
2. **Маршрут заявки.** Углублённая проверка назначается, если сработал хотя бы один признак: клиент или связанное лицо — PEP; юрисдикция из перечня повышенного риска; заявленный первый взнос выше порога; заявленный доход не согласуется с планируемым объёмом. Ни один не сработал — заявка идёт в рассмотрение, минуя шаг 6.

Данные самосертификации сверяются с данными из Didit. Расхождение по гражданству или дате рождения — повод для ручной проверки, а не для автоматического отказа: чаще это опечатка.

---

## 7. Шаг 5. Соглашения

- Шаблоны версионируются. Клиент подписывает **конкретную редакцию**, и она фиксируется вместе с хешем документа.
- Устаревшие редакции из списка на подписание исключаются, но остаются в журнале: важно, что на конкретную дату всё было подписано.
- Каждое действие пишется в журнал согласий: документ, версия, действие (`granted` / `revoked`), время.
- Отзыв согласия возможен и после подписания. Отзыв обязательного соглашения возвращает заявку на этот шаг и блокирует продвижение.
- Журнал доступен клиенту в «Документах» — это его доказательство не меньше, чем наше.

---

## 8. Шаг 6. Углублённая проверка

Анкета формируется шаблоном с версией; ответы сохраняются черновиком и отправляются одним действием. Вопросы бывают обязательными, поддерживают текст, выбор, дату и приложение файла.

При `AMENDMENTS_REQUESTED` клиенту возвращается **та же анкета с прежними ответами** и комментарием проверяющего. Заставлять заполнять заново то, что уже принято, — верный способ потерять клиента на последнем шаге.

---

## 9. Шаг 7. Рассмотрение

| Решение | Состояние | Последствие |
| --- | --- | --- |
| Одобрить | `APPROVED` | счёт открыт, доступ A4 |
| Запросить уточнения | `AMENDMENTS_REQUESTED` | возврат к шагу 6 с комментарием |
| Отклонить | `REJECTED` | повторная заявка через 30 дней |

Решение всегда сопровождается причиной. Причина по отказу показывается клиенту в формулировке, не раскрывающей методику скоринга: клиент должен понимать, что делать, а не как обойти проверку.

---

## 10. Сквозные правила

**Идемпотентность.** Все операции, меняющие состояние, принимают ключ идемпотентности. Повторная отправка формы при обрыве связи не создаёт вторую заявку.

**Гард на сервере.** Проверка порядка шагов на фронте — удобство, а не защита. Сервер отклоняет операцию шага, для которого не выполнены предыдущие, независимо от того, что показал интерфейс.

**Гонки.** Вебхук провайдера и резервный опрос могут прийти одновременно. Переход выполняется в транзакции со сравнением текущего состояния: применяется первый, второй становится безопасным no-op.

**Уведомления.** Каждый переход, требующий действия клиента, порождает уведомление: письмо, отметка на вкладке «Статус заявки» и, если подключён, Telegram. Следующий шаг открывается автоматически по завершении предыдущего.

**Хранение.** Персональные данные шифруются на уровне поля. Доступ комплаенса логируется. Срок хранения после отказа — по требованию юрисдикции, затем удаление.

## 11. Сроки

| Что | Норматив |
| --- | --- |
| Ссылка подтверждения почты | 24 часа |
| Повторная отправка письма | не чаще 1/минуту, до 5/сутки |
| Сеанс проверки Didit | 24 часа до `EXPIRED` |
| Ожидание вебхука до резервного опроса | 15 минут |
| Попыток проверки личности | 3, далее ручная проверка |
| Рассмотрение заявки | до 1 рабочего дня, автоодобрение — минуты |
| Повторная заявка после отказа | 30 дней |

## 12. Состояние реализации

**Реализовано:** машина из 15 состояний с историей переходов, порядок шагов и гард на фронте, экраны всех шагов, конфликт `409` при живом сеансе проверки, статусы сеанса включая `SUPERSEDED`, приоритет состояния заявки над данными сеанса, самосертификация с признаками PEP и санкций, версионирование соглашений с журналом и отзывом, анкета EDD с сохранением ответов, экран статуса с привязкой к шагу, выход из кабинета со сбросом сессии.

**Состояния вне линейного трека разбираются отдельно.** У `IDENTITY_FAILED`, `REVERIFICATION_REQUIRED`, `AMENDMENTS_REQUESTED`, `REJECTED` и `SUSPENDED` нет собственного шага в треке, поэтому каждому задан шаг-якорь (`OFF_TRACK` в `modules/onboarding/model/steps.ts`). Без якоря ни один шаг не совпадал бы с состоянием и весь трек рисовался «Ожидает», хотя регистрация и почта давно пройдены. Шаги за якорем сверяются с историей: отправленную анкету запрос уточнений не отменяет.

**Требует бэкенда:** выпуск и хеширование токенов почты, вебхуки сервиса доставки и обработка отказов, интеграция с Didit и проверка подписи вебхука, идемпотентность и резервный опрос, ограничение попыток проверки, заполнение профиля данными из проверки, маршрутизация в EDD по факторам риска, серверный гард шагов, автоодобрение, уведомления по переходам.
